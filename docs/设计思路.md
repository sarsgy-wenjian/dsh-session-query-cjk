# 设计思路

> 这份文档解释「为什么这么写」。要装、要用、要配，看 [README](../README.md)；要复现验收，看 [dev/README.md](../dev/README.md)。

## 0. 一句话

把「中文搜不到」拆成**三个互不相干的问题**分别解决，而不是换一个更重的检索方案（外部分词器、embedding、倒排重建）。

| 问题 | 现象 | 本包的对策 |
|---|---|---|
| A. 中文不可分词 | 搜两个字恒为 0 命中 | 字级索引（CJK 逐字成 token） |
| B. 说法与写法不一致 | 说「香包」原文写「香囊」 | 别名表，查询侧扩展 |
| C. 字错音对 | 语音转写／别字写错一个字 | 拼音归一，仅在别名表内做 |

三层是**加法**：A 让命中有可能，B／C 让命中变宽。

## 1. 问题 A：中文为什么搜不到

SQLite FTS5 的 `unicode61` 把「连续的 CJK 字符」切成**一个 token**。因此一篇文档里写了「林晚秋来了」，产生的 token 是 `林晚秋来了` 这一整串；这时搜「林」或「林晚秋」都匹配不上——除非那串恰好整个等于查询。

### 三种方案，为什么选第三种

| 方案 | 单字可搜 | 代价 | 结论 |
|---|---|---|---|
| **trigram 分词器**（本包旧版） | ✗（≥3 字符才出 token） | 库体积大，1—2 字查询恒 0 | 弃用 |
| **外部分词器**（jieba 等） | ✓ | 要带词典、绑定原生库或 WASM；升级宿主就得跟着适配 | 弃用 |
| **字间插入分隔符 ＋ `unicode61`** | ✓ | 库体积约原文 3 倍 | **采用** |

具体做法：写入前在每两个相邻 CJK 字符之间插入 `\u0001`，`unicode61` 就会把每个汉字切成独立 token；查询侧做同样切片，再包成 FTS5 **短语**（`"林\u0001晚\u0001秋"`）。短语要求 token **连续出现**，于是「短语匹配」等价于「原文子串匹配」——搜「林家」只命中真的连着写成「林家」的地方，不会命中「林……家」。

**为什么用 `\u0001` 而不是空格**

- `unicode61` 把标点与空白都当分隔符，用空格能达到同样效果，但会**毁掉原文里本来就有的空格**（中英混排、表格、代码）。
- `\u0001` 是不可见控制字符：既不参与分词，又不改变原文展示；写入与高亮两处都能原样还原。

**两侧对称是硬要求**

`sanitizeFtsText()` **写入和查询共用**，所以不会出现「索引按一个字、查询按整串」的错配。这比任何注释都可靠。

**代价与取舍**

- 库体积约原文 3 倍（88 个会话 → 约 88 MB，19,035 篇文档）。
- 单字命中面很宽（实测 2,220 篇 / 80 会话）。这不是 bug，是精确子串语义的必然结果；排序按 `match_count DESC, document_length ASC, time DESC, seq DESC`，让「命中次数多、文档短、时间近」的排前面。
- 高亮：`highlight()` 返回的文本带 `\u0001`，出摘要前用 `ungramCjk()` 还原。

## 2. 问题 B：别名层为什么只「追加」

别名表是**纯查询侧**的扩展：索引里永远只存原文。好处是

- 索引与别名表**完全解耦**：改别名表不需要重建库，改完下一个查询就生效（热更新，靠 mtime 判断）。
- 原词**永远保留**在结果里，别名只追加候选（最多 6 个，`OR` 并查），所以别名写歪了最多是「没变宽」，不会「把对的挤掉」。
- 键里含某个别名时也触发替换（如「香包链」→「香囊链」）。

**为什么不内置业务词库**：术语是会跑偏的，猜错比不猜更贵。所以默认内置空表，只给约定路径；用户自己写。

## 3. 问题 C：拼音层为什么只覆盖别名表

拼音层的做法是：把查询按字查表得到音节 → 归一 → 拿归一后的键去 `PY_INDEX` 找候选词。而 `PY_INDEX` **只由别名表中的词构建**。

- 收益：零误伤（只在你登记过的实体之间做同音替换）、零额外索引（不占库体积）。
- 代价：别名表里没有的实体，拼音帮不上忙。

**为什么不建全库拼音索引**：要给每篇文档算拼音键并单独建表，写放大与库体积都明显上升；而短查询（1—2 个音节）在同音空间里噪声极大——「林晚秋」和「林万秋」在归一后完全一样，全库范围几乎必然捞出无关内容。宁可窄而准。

归一规则（针对中文口语输入的实际错误）：

| 归一 | 覆盖的输入问题 |
|---|---|
| `zh / ch / sh` → `z / c / s` | 平翘舌不分 |
| `n` → `l` | n/l 不分 |
| `ang / eng / ing / ong` → `an / en / in / on` | 前后鼻音不分 |
| `ü` → `u` | ü 打不出来 |

多音字只取 Unicode Unihan `kMandarin` 的**主读音**，所以「长」「重」这类字可能漏一种读法——已知取舍，见 README「已知限制」。

## 4. 与宿主的契约

本包是 `@deepseek-ai/dsh-session-query-sqlite` 的**同接口替换**，挂同一个 `ctx.sessionQuery` 服务：

| 宿主调用 | 本包的实现 |
|---|---|
| `listSessions()` | 继承基类 `SessionCorpus`：live 会话优先，persistence 兜底 |
| `searchSessions(request)` | 查 FTS5，`ROW_NUMBER() OVER (PARTITION BY session_id ...)` 每个会话只留最强命中 |
| `searchEvents(request)` | 同一批文档，限定单个会话，按事件排序 |

**事件过滤由宿主给**（`type ∈ {user/message, assistant/message}`、`surface = current`），插件只负责执行——这条边界很重要：**可见性/权限判断在宿主，插件不做二次判定**。

**游标与代次（generation）**：游标里带 `instance`、`scope`、`fingerprint`（请求指纹）、`generation`（索引代次）和 offset。reconcile 推进代次后，旧游标会因代次不符被判为陈旧并重来，避免「翻页翻到半途索引变了」导致的错页/漏页。

**reconcile**：每次检索前对齐一次——listing 里 revision 变了的会话重写该会话的全部文档；已消失的会话连同文档一起删；live 会话放 `temp` 表并用内容 fingerprint 判断是否重写。这样索引最终一致，且写放大只落在变过的会话上。

**`openAt` 为什么默认 `first-search`**：启动阶段 `sessions`/`persistence` 可能尚未就绪，此时建库会得到一个**0 会话 0 文档的空库**（本机实测过）。懒建能避开这个时序坑。

## 5. 配置原则（0.3.1 的教训）

**默认值只有一处真相：`static Config` 的 schema。**

cordis 在**构造实例之前**就按 schema 校验并填默认值，所以构造函数／`resolveConfig()` 里的 `config.x ?? fallback` 对「用户没写」**永远不触发**。0.3.0 同时犯了两个错：

1. `path` 写成 `z.string().required()` → 用户不写 `path` 时校验直接抛错，插件**起不来**（回落逻辑根本没机会跑）；
2. `openAt` 的默认值改在构造函数里 → schema 仍填 `startup`，改的那行是死代码。

0.3.1 起，默认值一律写在 schema 里，构造函数只做「空串 → 约定路径」这一层归一。

## 6. 明确的非目标

- **不改客户端 UI**：搜索入口在哪儿、结果最多显示几行，由宿主决定（见 README「已知限制」）。
- **不内置业务词库**。
- **不做全库拼音索引**。
- **不做文件级增量扫描**：索引是「检索时对齐」的快照模型，不常驻监听会话写入。

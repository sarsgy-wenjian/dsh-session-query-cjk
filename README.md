# dsh-session-query-cjk

让 DeepSeek Harness 的中文会话搜索真正可用。

> 想先看「为什么这么设计」：[`docs/设计思路.md`](docs/设计思路.md)｜版本变更：[`CHANGELOG.md`](CHANGELOG.md)｜零配置实测：[`docs/验收-零配置与搜索入口-20261115.md`](docs/验收-零配置与搜索入口-20261115.md)

官方后端用 SQLite FTS5 的 `unicode61` 分词器，中文整串会被当成**一个 token**——同一个连续中文串只能整体命中，正文里零散写过的字词基本搜不到。这个包替换掉这层后端，补上三层能力：

| 能力 | 解决什么 |
|---|---|
| **汉字级索引** | 1 个字起就能搜，搜「林」不需要凑够三个字 |
| **口语别名扩展** | 你说「香包」，原文写「香囊」，也能搜到 |
| **拼音模糊匹配** | 打错字但读音对，照样找得到（大舌头、语音转写场景） |

三层叠加，一条链：**索引切到字为单位 → 查询时展开同义/同音候选 → OR 并查**。

## 实测效果

下列数据来自本机真实索引库（**88 个会话、19,035 篇文档、88.0 MB**），查询方式与插件内部一致（汉字间插入分隔符后包成 FTS5 短语）：

| 查询 | 说明 | 命中 |
|---|---|---|
| 林 | 单字 | **2,220 篇 / 80 会话** |
| 林家 | 双字 | **628 篇 / 69 会话** |
| 林晚秋 | 三字 | **1,609 篇 / 80 会话** |
| 苏晴岚 | 三字 | **2,411 篇 / 80 会话** |
| 册子 | 口语词（库内原样存在） | **221 篇 / 54 会话** |
| 香包 | 原词 0 篇，别名扩展为「香囊」 | **2,494 篇**（别名生效） |
| 林晚丘 | 库内无此字，拼音回落至「林晚秋」 | **与林晚秋结果一致**（拼音生效） |
| abcdef999 | 不存在的字符串 | **0 篇** |

> **上表后两行需要别名表。** 拼音层只在**别名表内部**做同音归一（见下文「拼音模糊规则」），所以别名表里没有的实体拼音层帮不上忙。别名表默认看 `~/.dsh/cache/session-query-aliases.json`，放好就生效，不用写配置。零配置（不写任何 config）下的实测结果见 [`docs/验收-零配置与搜索入口-20261115.md`](docs/验收-零配置与搜索入口-20261115.md)：不放别名表时「香包」「林晚丘」都是 0；放一张只含 `香包→香囊` 与 `林晚秋→林晚秋` 的表后，两者立刻出 5 条。

其中最后三行是三层能力各自的直接证据：
- 「香包」在库里一次都没出现过，能出结果全靠别名层把它换成「香囊」；
- 「林晚丘」这个名字在库里不存在，能出结果全靠拼音层把它归一到 `lin|wan|qiu`，与「林晚秋」同键；
- 单字、双字能出结果，靠的是字级索引（旧版 trigram 方案下这两项恒为 0）。

## 安装

### 环境要求

| 项 | 要求 | 说明 |
|---|---|---|
| Node（插件侧） | **≥ 22.13** | 插件用内置 `node:sqlite`：v22.5 出现但需 `--experimental-sqlite`，v22.13／v23.4 起免 flag。推荐 24.x |
| Node（用 npm 装 DSH 命令行时） | **≥ 24.9** | `@deepseek-ai/dsh` 自己的 `engines` 要求，低于此装不上 |
| DeepSeek Harness | 0.2.2-rc.3 | `peerDependencies` 钉的就是这个版本 |

> 踩过的坑：Ubuntu 22.04 云主机默认 PATH 里的 Node 常是 22.x 基线版本，可能低于上面要求。装之前先 `node -v`；机器上常另装有 `/opt/nodejs/24` 之类的路径，把它前置到 PATH 即可。

### 方式 A：一键安装（推荐）

本包声明了 `dsh.bundle`，装为 bundle 即可，**补丁会自动禁掉官方后端并启用本包**，不用手工改任何配置：

```
plugin_manager install_bundle
  target: git+https://github.com/sarsgy-wenjian/dsh-session-query-cjk   ← 或 dsh-session-query-cjk（已发 npm 时）
```

装完重启一次，首次搜索时自动建库。

### 方式 B：手工安装（没有 git、或想自己控制配置时）

**1. 放进 profile**

```
%USERPROFILE%\.dsh\profiles\<profile名>\node_modules\dsh-session-query-cjk\
```

把整个包目录放进去，确认 `lib/index.js` 和 `lib/pinyin-data.json` 都在。

**2. 改 profile 的 `cordis.patch.yml`**

在 profile 目录的 `cordis.patch.yml` 里追加两项：**禁用官方后端**，**插入本包**（内容与本包的 `cordis.patch.yml` 相同）。

```yaml
- id: session-query-sqlite
  name: "@deepseek-ai/dsh-session-query-sqlite"
  disabled: true

- insert:
    - id: session-query-cjk
      name: dsh-session-query-cjk
```

> **`config` 整段都可以不写**（零配置）：索引库落 `%USERPROFILE%\.dsh\cache\session-query-cjk.db`，别名表看 `%USERPROFILE%\.dsh\cache\session-query-aliases.json`，两者目录都会自动创建。实测见 [`docs/验收-零配置与搜索入口-20261115.md`](docs/验收-零配置与搜索入口-20261115.md)。
> 如果写了 `path`，注意 YAML 单引号内的反斜杠不需要转义。

### 3. 重启

关闭 DeepSeek Harness 再打开。**首次搜索时开始建索引**。

首次建库需要一点时间（本机 88 个会话、19,035 篇文档约 1 分钟）。之后走持久库，不再重建。

索引库大小约为原始文本的 3 倍，本机实测 88.0 MB。如果磁盘紧张，可以删掉这个 `.db` 让它重建。

## 配置项

| 配置 | 默认 | 说明 |
|---|---|---|
| `path` | `~/.dsh/cache/session-query-cjk.db` | 索引库路径，**可省略** |
| `openAt` | `first-search` | 建库时机：`startup` / `first-search` / `never` |
| `journalMode` | `wal` | SQLite 日志模式 |
| `defaultLimit` | 20 | 默认返回条数 |
| `maxLimit` | 100 | 单次上限 |
| `snippetChars` | 240 | 摘要片段长度 |
| `aliasFile` | `~/.dsh/cache/session-query-aliases.json` | 别名表 JSON 路径，**可省略**；不写就用这个约定路径（文件不存在＝不扩展） |
| `pinyinFile` | 空 | 拼音表路径，留空则用包内自带的 `lib/pinyin-data.json` |
| `vocabFile` | `~/.dsh/cache/session-query-vocab.json` | 语料拼音词表路径，**可省略**；不写就用这个约定路径（文件不存在＝只退别名表拼音层） |
| `relax` | `auto` | 零命中时是否自动「放宽一字」：`auto` / `off` |

**关于 `openAt`**：默认值取 `first-search` 而不是 `startup`。原因是启动阶段 sessions 服务可能尚未就绪，此时建库会得到一个**0 会话 0 文档的空库**（本机实测过）。`first-search` 等首次真正搜索时再建，能避开这个时序问题。

`aliasFile`、`pinyinFile` 和 `vocabFile` 都支持**热更新**：改了文件立即生效，不用重启。`aliasFile` 指向的文件不存在或格式损坏时，插件只退回「不做别名扩展」，**不会崩溃**。

## 零命中时的放宽回退（0.4.0 起）

原词在索引里 0 命中时，插件**再试一轮**，按由窄到宽的顺序找：① 去掉句首句尾的标点括号（`（1845年那一夜。）`→`1845年那一夜`）；② 取句子前/后 3—4 个字的窗口；③ 逐字删掉一个汉字（错字/多字）。最多 10 个候选，每个候选至少 3 个字、至少 2 个汉字（纯数字或单字碎片不拿来凑数），命中即返回。

例：查「设计稿子」原词 0 条 → 删掉「子」得「设计稿」命中；查「（1845年那一夜。）」原词 0 条 → 放宽为「那一夜」命中。

- 放宽结果**单页返回、不带翻页游标**，返回对象多一个 `relaxedQuery` 字段，写明实际使用的词。
- 摘要前面会加一段标记：**〔放宽为「那一夜」〕**——黑鲸侧栏搜索框虽然不转发 `relaxedQuery`，但摘要里的这段文字会照常显示，所以界面里也能看清放宽成了什么。
- 关掉：配置 `relax: off`。

## 别名表格式

**放哪儿**：不写 `aliasFile` 时，把文件放 `%USERPROFILE%\.dsh\cache\session-query-aliases.json` 即可自动加载——**零配置也能用别名和拼音**，不用改 `cordis.patch.yml`。想放别处再写 `aliasFile`。

一个普通 JSON 对象，键是「你可能输入的说法」，值是「要一起搜的正式名」：

```json
{
  "香包":   ["香囊"],
  "册子":   ["图册"],
  "惠兰":   ["李蕙兰"],
  "林氏":   ["林家"]
}
```

规则：

- 原词**始终保留**在结果里，别名只做追加，不会把原来的结果挤掉。
- 单次查询最多扩展成 6 个候选，用 ` OR ` 连接。
- 键里含有某个别名时也会触发替换。
- 以 `_` 开头的键视为注释，插件会跳过。

值的语义有两类，功能上没区别，但维护时建议分清楚：**错写纠正**（惠兰 → 李蕙兰）和**同义/异名**（香包 → 香囊）。

> 别名表需要自己维护，插件不内置业务词库。不配别名表就只有字级检索与语料词表拼音扩展；**别名扩展**需要别名表。

## 拼音模糊规则

不是全拼精确匹配，而是先做声母韵母归一，再比较：

| 归一 | 覆盖的口音问题 |
|---|---|
| `zh / ch / sh` → `z / c / s` | 平翘舌不分 |
| `n` → `l` | n/l 不分 |
| `ang / eng / ing / ong` → `an / en / in / on` | 前后鼻音不分 |
| `ü` → `u` | ü 打不出来 |

所以「林晚秋」「林婉」「林婉」「林晚丘」在归一后都是 `lin|wan|qiu`，全部能匹配到「林晚秋」。

**范围**：拼音匹配只在**别名表里的词**与**语料词表里的词**之间做——不是全库拼音索引。好处是零成本、零误伤；代价是两张表里都没有的词，拼音层帮不上忙。

### 直接敲拼音（0.4.1 起）

查询是**纯字母**时（`liuxiahui`），插件先按音节表做切分（`liu | xia | hui`），逐音节归一后查拼音索引（别名表优先、语料词表兜底），命中就展开成汉字实体再检索。

| 输入 | 展开 |
|---|---|
| `linwanqiu` | 林晚秋 |
| `liuxiahui` | 柳夏辉（语料词表里有这个词即可，不用登记别名） |
| `wangqiu` | 林晚秋（表里登记了「晚秋」→「林晚秋」时） |

切分用的是**回溯**而不是最长匹配：`xian` 既可切成 `xian` 也可切成 `xi｜an`，以能否命中拼音索引为准。

**范围**：别名表里登记过的实体＋语料词表里的词都能被拼音展开（见下一节）。两张表都没有的词，敲拼音仍是 0 命中——这正是「不瞎猜」的边界：语料里从没出现过的词，展开成同音字也查不到东西。

### 语料拼音词表（0.5.0 起）

只靠别名表，表外的名字（比如稿子里出现过的角色、地名）敲拼音查不到。0.5.0 起插件支持一张**语料拼音词表**：从使用者**本机的会话索引库**自动抽取「真实出现过的中文词」，按归一拼音键聚组、按文档频排序，生成 `session-query-vocab.json`。

- **词表不进包、不上传**：它是从你自己的索引库生成的私有数据，包内不携带任何语料，也不会随 npm 发布。
- **生成方式**（仓库 `dev/build-vocab.mjs`，不随包分发）：
  ```powershell
  node dev/build-vocab.mjs
  # 默认：读 ~/.dsh/cache/session-query-cjk.db
  #       写 ~/.dsh/cache/session-query-vocab.json
  #       只抽 user/message + assistant/message（工具输出噪音默认排除）
  ```
  索引重建（新会话进库）后重跑一次即可刷新词表。
- **候选按频次排序**：每个拼音键最多保留 8 个词，高频词在前；`liuxiahui → 柳夏辉`、`xiangnang → 香囊` 这类直接命中。
- **与别名表的关系**：别名表优先，词表兜底。别名表适合手工纠正错写/异名（香包→香囊）；词表适合让「会念不会写」的任意语料词自动可查。

## 原理

**字级索引**：写入前在每个相邻汉字之间插入分隔符 `\u0001`，`unicode61` 就会把每个汉字切成独立 token。查询端做同样切片，再包成 FTS5 短语。短语要求 token 连续出现，因此**等价于原文子串匹配**——搜「林家」只会命中真的连着写成「林家」的地方。

用 `\u0001` 而不是空格，是为了不破坏原文里汉字之间本来就有的空格。

这个改动落在 `sanitizeFtsText()` 里，而该函数**写入和查询共用**，所以两侧天然一致。

**别名与拼音**：`quoteFtsData()` 把用户输入还原成原文 → 查别名表 → 再做拼音归一匹配 → 合成多个 FTS5 短语用 `OR` 连接。

## 已知限制

- **DeepSeek Harness客户端只负责"入口"，结果条数由它自己的合并逻辑决定。** DeepSeek Harness 0.2.2-rc.3 的入口仍然在：侧边栏「会话／工作区」分组标题行右侧的**放大镜按钮**（侧边栏展开时才渲染），或直接按 **Ctrl+K**（web 版是 Ctrl+Alt+K）。输入后走 Host 的 `session.search` → 本插件的 `searchSessions`。
  客户端只渲染它自己会话列表里存在、且未被归档过滤掉的会话，合并后的行数上限是 **20**（`SESSION_SEARCH_RESULT_LIMIT`）；因此"后端命中 80 个会话、界面只列 N 条"是**客户端的可见性过滤＋上限**，不是索引漏了。要完整结果，直接用 Agent 侧工具或查询索引库。
- **单字查询命中面很宽**（搜「林」有 2,220 篇）。这是精确子串语义的必然结果，不是 bug，结果按相关性排序。
- **拼音只覆盖别名表与语料词表里的词**，不是全库拼音索引；词表里的候选按文档频排序，低频词可能排在后面或被 `min-count` 过滤（构建脚本默认要求至少出现在 2 篇文档里）。
- **多音字只取主读音**（拼音表来自 Unihan `kMandarin`），「长」「重」这类多音字可能漏一种读法。
- 首次建库有时间成本；索引库是**快照**，DeepSeek Harness产生新会话后需要重建（删掉 `.db` 或等增量刷新）才能搜到。
- DeepSeek Harness升级后若官方 `SessionQueryEngine` 接口变动，需要重新适配。
- 别名表需人工维护；语料词表由 `dev/build-vocab.mjs` 从本机索引库自动生成（覆盖「语料里真实出现过的词」，非手工纠错场景优先用它）。

## 附属工具（不属于本包）

本包**只包含会话全文检索**。下面这些能力依赖外部运行时，**没有打进 npm 包**，放在独立目录单独维护：

| 工具 | 作用 | 依赖 |
|---|---|---|
| `find_attachments.py` | 检索 PDF / 图片 OCR 文本 | Python、pypdf |
| `ocr_image.ps1` | 图片 OCR（Windows 内置引擎） | Windows + PowerShell 5.1 |
| `build_attachment_session.py` | 把 PDF/图片文本整理成检索索引 | Python、pypdf、zstandard |

它们仅在本机 Windows 环境验证过（Windows OCR 语言仅 `ja`、`zh-Hans-CN` 可用），**不可跨平台**，也不参与插件生命周期。如果你的需求只是会话检索，不需要它们。
